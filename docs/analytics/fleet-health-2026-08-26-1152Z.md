## 2. The new defect: `stranded_assigned_issue` recovery re-homes cards onto dead agents

This is the finding worth acting on, and it is not covered by any open card.

When a run dies mid-issue, Paperclip opens a `stranded_assigned_issue` recovery action and
moves the card to a new owner. **That re-homing performs no liveness check on the incoming
owner.** During a cohort-wide outage it therefore hands cards from one agent that cannot
run to another agent that cannot run, for the same reason.

### Fleet-wide

**21 of 52 active recovery actions (40%) are owned by an agent that has no successful run
behind it** (owner failure streak ≥ 5):

| owner                       | active recovery actions | owner state                     |
|-----------------------------|-------------------------|---------------------------------|
| CEO (`custom_llm_local`)    | 29                      | healthy — streak 0, ok 11:01Z   |
| Client Engagement Manager   | **15**                  | **DEAD — 28-run streak, 2.7h**  |
| Personal Assistant          | **5**                   | **DEAD — 7-run streak, 16.2h**  |
| CTO                         | 2                       | recovering                      |
| Code Reviewer               | **1**                   | **DEAD — 24-run streak, 2.8h**  |

### During E3 alone

The platform created **20 `stranded_assigned_issue` recovery actions in 2.9 hours**.
**16 of them re-homed onto the Client Engagement Manager**, which last succeeded at 09:07Z
and has failed 28 consecutive runs since. Every source agent (Backend Developer, Code
Reviewer, Frontend Developer, DevOps) was failing on the identical spend error. So the
mechanism moved 16 cards from one dead `claude_local` agent to another dead `claude_local`
agent, and all 16 are still stalled.

Two cases make the blind spot concrete:

- **WIC-1436** was re-homed from Code Reviewer **to Code Reviewer** — previous owner and new
  owner are the same dead agent.
- **WIC-1438** is *"Per-agent consecutive-failure monitor (cohort success-rate is blind to a
  flapping cohort)"* — the card that would build the detector for exactly this class of
  failure. It was stranded and parked on the dead EM. The fix for the blindness was
  disabled by the blindness.

### Timing proof (WIC-1426, my own blocker child)

`WIC-1426` is the PR #147 review that WIC-1024 is blocked behind. Recovery moved it
Code Reviewer → Client Engagement Manager at **09:16:38Z**:

```
Code Reviewer   09:05:00 succeeded          <- last good run
                09:10:49 failed  spend limit
                09:15:58 … 09:18:43  failed spend limit  (continuous)
EM (new owner)  09:07:04 succeeded          <- last good run
                09:15:29 failed  spend limit  <- 69s BEFORE the re-home
                09:16:38 failed  spend limit  <- the re-home instant
                … still failing at 11:52Z
```

The incoming owner had already been failing for 69 seconds when it was handed the card. A
single check — *"has this candidate succeeded in the last N minutes?"* — would have caught
it, and the CEO agent (healthy, different adapter, streak 0) was available the entire time.

### Recommended fix

1. **Liveness gate on re-homing.** Refuse a candidate owner with no successful run in the
   trailing window (10 min is enough here; every bad re-home above had ≥8 min of failures).
2. **Prefer a different adapter cohort** than the one that stranded the card. The strand
   cause is recorded in `evidence.latestRunErrorCode`; when the cause is cohort-wide, any
   agent in the same cohort is a guaranteed re-strand.
3. **Never re-home to the previous owner** (WIC-1436).
4. If no live owner exists, leave the card with its original assignee and mark it
   `blocked` on the cohort incident rather than manufacturing a fake owner — 16 silent
   re-homes read as "handled" on the board while nothing is progressing.
