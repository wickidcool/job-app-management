### Fixed — onboarding no longer opens over an established user's dashboard (2026-08-26)

WIC-238 AC-10 requires that a user with at least one resume or one application is never shown onboarding. Nothing implemented it. `shouldShowOnboarding` read only the `onboarding_status` table, so the returning-user branch did not exist; and the web client never called `should-show` at all — `onboardingService.shouldShow()` was dead code, and `OnboardingContext` decided visibility itself from `completedAt`/`currentStep`. Since `GET /users/me/onboarding/status` auto-creates a `welcome` row for any user without one, every user who predated the feature got a row created for them on page load and then the modal on top of their populated dashboard. Silent by construction: users read it as a new feature rather than a bug, and developers never saw it because their own accounts already had a row from earlier testing (WIC-1359, found by QA on WIC-1354).

- **The bypass is scoped in time, not by engagement.** The naive reading of AC-10 — count resumes and applications, return false if either is non-zero — introduces a worse bug than it fixes: onboarding step 3 *is* the resume upload, so a genuine new user would be ejected from the flow at the moment the flow's own step succeeded. But scoping by engagement instead is also wrong, and in the same direction as the original bug: the modal this fixes is a thing affected users can click, and one press of "Get Started" or "Skip for now" POSTs progress, so an engagement short-circuit would leave every established user who touched it once getting onboarding over a populated dashboard indefinitely. The discriminator is `onboarding_status.started_at`. Work created *before* the status row cannot have come from the flow, so for a user the flow has moved at least one step the probes carry `uploaded_at < started_at` / `created_at < started_at`. For a user the flow has never moved — no row, or a pristine `welcome` one — there is no flow output to exclude and the probes stay unbounded, deliberately: bounding them there would drag back a new user who dismissed at `welcome` and then created an application by hand.
- **The pristine-row case is the one users actually hit.** Established users who opened the app before this shipped all have an auto-created `welcome` row, so "no row" alone would have missed the entire affected cohort — they stopped looking like new users the first time they loaded the page.
- **Visibility is now the server's answer on the client too.** `OnboardingContext` fetches `should-show` alongside `status` and uses it directly. A server-only fix would not have closed this, because the client never asked. The two requests race deliberately: if `should-show` lands before `/status` has auto-created the row it reads "no row" instead of "pristine row", and the service answers the same either way.
- **The mount and refetch paths now share one implementation.** They were duplicated, and it was the copy inside the mount effect that derived visibility locally. They differ only in the loading flag, which the mount path must not set synchronously inside an effect body.
- **Existence probes, not counts** — `select id … limit 1` on each table, resume first, short-circuiting the second round trip. A completed user still costs exactly one query. The `user_id` equality is index-backed on both tables (`idx_resumes_user_id`, `idx_applications_user_id`); there is no composite over the timestamp, so the `started_at` bound is a filter over one user's rows rather than a range scan, and no index was added for it — with `limit 1` over a single user's history the worst case is scanning that user's own rows.
- **The two WIC-1354 tests that pinned the gap are replaced by tests that pin the fix.** The `it.fails` AC-10 case is now a passing assertion, and the sentinel that asserted "consults only `onboarding_status`" — true of the defect — is now a per-scenario query-count assertion: 1 select for a completed user, 2 when a resume short-circuits, 3 for a user with no row and no history, 3 for a mid-flow user (history *is* consulted mid-flow, just bounded by `started_at`). Because the db double resolves rows whatever the predicate says, those counts cannot see the bound at all: two further tests render the captured `where` clause to SQL and assert the bound is present on the engaged path and absent on the pristine one. Reversal-checked in three directions — restoring the unconditional `return true` on the engaged branch fails 5 tests, dropping the `started_at` bound fails 1, and over-applying it to the pristine branch fails 1. 488 API tests pass.

### Added — `restoreFocusTo` now has a stated obligation, and a check that will enforce it (2026-08-29)

`MODAL_FOCUS_MANAGEMENT_SPEC.md` §5.1 and §5.2 both answer *which* element to pass to `ConfirmationModal`'s `restoreFocusTo` — but only once you have already decided you need to pass one. Nothing stated *when* a fallback is obligatory, and the prop is optional (correctly: a cancel-only dialog whose trigger survives must not be forced to name one). So a future call site whose confirm action destroys its own trigger reintroduces WIC-1181 with no type error, no lint error and no failing test. New §5.3 states the obligation, and `docs/design/confirmation-modal-focus-audit.py` makes it a red check rather than a hope (WIC-1670, from the Code Reviewer's non-blocking note on PR #115).

- **The obligation is written as a structural test on the render tree, not a judgement about the trigger.** The natural question — "is the trigger detached when the dialog closes?" — is the wrong one and has already misled two reviews: it usually is *not* detached, because the failure is an ordering race in which the restore succeeds and is undone a macrotask later (§4.2). §5.3 asks instead **"does the trigger render inside anything the action's refetch re-renders?"**, which an author can answer by reading their own JSX. A per-row control inside a `.map()` over the mutated collection always answers yes; so does a control inside any arm of a branch whose predicate the action can flip.
- **The three non-remedies are named**, because all three were tried: an `isConnected` guard (passes, because the node is still connected when it runs), declining to `preventDefault()` (Radix's own handler prevents anyway and focuses an always-`null` ref), and a manual pass that looked fine (the damage lands after the decision point).
- **Enforcement is a declaration, not an inference.** A lint rule would have to decide whether a dialog's `onConfirm` unmounts its own trigger — data flow across a mutation, a query invalidation and a conditional render, not statically decidable. And making the prop *required* would be worse than the status quo: authors would satisfy the type with a throwaway ref, converting a visible omission into an invisible dead ref, which is §5.1 rule 2's failure mode on purpose. So every `<ConfirmationModal>` call site must instead either pass the prop or carry a `focus-restore-exempt` comment saying why its trigger survives. Reasons under 40 characters are rejected — "cancel only" is a shrug, not a declaration.
- **The audit is dormant at this commit, and says so on every run.** `restoreFocusTo` does not exist on `main` yet; it lands with PR #115. Rather than fail the build on a compliant-by-absence tree or pass silently, the script prints a `NOTICE` naming every unenforced call site (one today, `ResumeManager.tsx:176` — the one whose trigger the action destroys) and exits 0. It arms itself automatically on the commit that declares the prop. This deliberately avoids touching `ResumeManager.tsx`, which PR #115 is currently editing.
- **What the green check does not cover is stated in the script and in the spec.** It cannot tell whether the ref you passed is any good — that the fallback renders on both arms of the branch, and is non-`null` at close time, are §5.1 rules no grep can check. It covers `ConfirmationModal` call sites only, while the rule itself is normative for all six dialogs. Verified end-to-end against PR #115's head, where it goes green on the real compliant call site, and against synthetic call sites for each failure path: bare, short-reason, well-reasoned exemption, and an unparseable tag.
- **The UI/UX workspace copy of the spec is now marked superseded.** Two copies of a normative document is how §5.3 would have ended up in the one nobody can open.

### Fixed — the changelog duplicate check could not see the failure mode it was written for (2026-08-29)

Root `CLAUDE.md`'s "Check what the driver did" detector counted **byte-identical** stripped lines. The first failure mode named two paragraphs above it is *"both sides revised the same existing entry — union keeps both revisions"*, and two revisions of one bullet are by definition not byte-identical, so the check was blind to the class it was partly written for. It also never looked at `### ` headings at all, which is where a whole-entry double-ship shows up (WIC-1687, found by the Frontend Developer while fixing WIC-1684).

- **It now compares a normalised 70-character prefix, and checks headings as well as bullets.** The tradeoff is stated in place: a prefix match also flags genuine pairs that merely open the same way, so the discriminator is the tail, not the prefix. The two known-benign pairs currently on `main` are named so the check has a meaningful pass condition, and a duplicate `### ` heading is called out as having no benign case.
- **A third failure mode is documented: one side moves a block, the other edits inside it.** The two do not align as one diff3 region, so union keeps the relocated copy *and* the edited copy. The sting is that **moving a block is the documented remedy for the ordering defect**, so fixing one failure mode arms another for the next branch to touch that entry. Caught on PR #212 before merge (WIC-1692): its base branch had relocated an entry while #212 added a bullet inside it, and the union result carried the whole `### Security — Resume-variant and interview-prep reads…` entry twice, with the surviving second copy silently missing the hijack disclosure that entry exists to record.
- **The check is now runnable before you push, not only after you merge.** A clean `main` says nothing about what is queued to land on it — the corruption exists only in the merge *result*, and both parents can be individually spotless. The section carries a `git merge-file --union` simulation, with the warning to run it against the PR's **true base** rather than `main`, since simulating a stacked PR against `main` manufactures duplicates that will never ship.
- **Verified by extracting the embedded block from `CLAUDE.md` and running it verbatim**, rather than by eye: it returns `duplicate headings: none` and exactly the two documented benign bullet pairs on `main` @ `e0897df`, and as a positive control it fires on the reconstructed #212 union with `duplicate headings: {'security  resumevariant and interviewprep reads are sco': [11, 32]}` — which the previous byte-identical check reports as no headings at all.

Documentation and tooling only. No code, no tests, no behaviour change.

### Fixed — the changelog check reported ten branches as damaged when nine of them repair themselves (2026-08-30)

Root `CLAUDE.md` told readers that when a duplicate is already committed on a branch rather than introduced by the union merge, "re-merging `main` will not help." That is false, and false in the direction that turns a detector into an accusation generator. Ten open PRs still carry the WIC-1319 retracted fit-tier claim that PR #204 deleted from `main`; **nine of the ten lose it automatically the next time `main` is merged in.** The previous revision would have had someone file cards on all ten (WIC-1677).

- **The discriminator is one question, and the section now leads with it: is the offending text in `git merge-base origin/main <branch>`?** If it is, `main`'s correction is a deletion relative to a shared ancestor — a one-sided change that the three-way merge applies cleanly, without ever consulting the union driver. The branch is a passenger and owes nothing. If it is not, the branch introduced the text itself, `main`'s deletion has nothing to attach to, and no amount of merging forward will remove it. Measured across the ten: mergebase=1 on #123, #146, #180, #183, #188, #191, #215, #222 and #239; mergebase=0 on #117 alone.
- **What an owner looks like is a committed union result.** PR #117 took its copy inside merge commit `508289b`, which merged `fix/wic1309-fit-tier-blurbs` into `copy/wic1318-fit-tier-blurbs` while the source branch still held the retracted wording. That source branch has since been corrected and measures clean today, but #117 committed the driver's output and thereby converted a transient merge artifact into a branch-side addition. The generalisation is now stated in the file: the union driver's damage becomes permanent at the instant it is committed, which is the concrete reason to simulate before pushing rather than trust a clean `git merge`.
- **The self-heal test runs against `origin/main`; the union simulation runs against the PR's true base.** They disagree deliberately, because they ask different questions — the simulation asks what a merge will produce and needs the base that merge uses, while the self-heal test asks where the correction lives, and it lives on `main`. A stacked PR whose immediate base still carries the stale text is not thereby an owner: #191 and #123 both show the duplicate in a union against their own bases and are passengers against `main`.
- **The previously filed set was measured again and neither member survives.** The 2026-08-29 entry named PRs #146 and #160. #146 is a passenger; #160's branch is at `494d49d` and now contains zero occurrences, its author having repaired it. This is the second consecutive tick in which an accusation about a peer's branch decayed before it could be acted on, so the file now carries the round-trip confirmation as well as the count comparison.
- **Verified by extracting the new `bash` block from `CLAUDE.md` and executing it verbatim**, which reproduces the `pr/146 mergebase=1 branch=1` / `pr/117 mergebase=0 branch=1` split the prose quotes. Round trip on both, merging `main` into the branch and that result back into `main`: #146 ends at zero occurrences with the detector clean, #117 retains the retracted claim and both `SAME-ENTRY` bullet pairs. `main` itself is clean — the sweep returns `duplicate headings: none` and only the two documented benign `distinct entries` pairs at 0.40 and 0.50.

### Fixed — a decorative ✓ could land in a STAR field's accessible name (2026-08-29)

`STARInput` marked a valid field with `<span aria-label="Field valid">✓</span>`. The span has no `role`, so it maps to the ARIA `generic` role, whose name-from-author is **prohibited** in ARIA 1.2 — assistive tech may honour that `aria-label` or ignore it, and both readings are conformant. Because the span sits inside the `<label>` that names the textarea, the two readings produced two different accessible names for the form control: `"Situation: … Field valid"` when honoured, `"Situation: … ✓"` when dropped. Closes WIC-1191, the second and last member of the class opened by WIC-1185 (`ChangeActionBadge`, PR #101).

- **The glyph is now decorative and the status is real text.** `<span aria-hidden="true">✓</span>` plus a `sr-only` "Field valid" — no ARIA naming on a `generic` element, so the field's accessible name is stable at `"Situation: … Field valid"` under either reading. This is the worse variant of the class and needed the opposite remedy to WIC-1185: there the fallback text was the meaningful label `Create`, so dropping the attribute was sufficient; here the fallback was a bare tick that polluted a form control's name, so the status had to be re-expressed as text rather than merely unlabelled.
- **The class is closed, and the scan that says so is multi-line aware.** A tag-aware sweep of every `.tsx` in `packages/web/src` — matching opening tags across line breaks, not `aria-label` lines in isolation — finds zero remaining `generic` elements carrying an author name. The single-line grep the original ticket used would have missed any site whose attributes wrap, so the count is re-derived rather than inherited.
- **Both halves are now pinned by tests, asserted on behaviour rather than markup.** `src/test/prohibitedName.ts` strips prohibited names to model the AT that ignores them, and the tests assert the accessible name both before and after: it must name the field valid and must never contain the glyph, under either reading. Asserting `not.toHaveAttribute('aria-label')` would instead go green again the moment the attribute returns in another shape. Reversal-checked — restoring the old markup fails 2 of the 4 `STARInput` tests, with the pre-fix name reported as `"Situation: What was the context or challenge you faced?✓"`, reproducing the ticket's measurement in-repo.
- **Accessible names are read through jest-dom's `toHaveAccessibleName`, not `dom-accessibility-api` directly.** The latter is only a transitive dependency here, and its `package.json` `exports` block hides its own `.d.ts` from `tsc` — a direct import resolves to `any` and fails `tsc -b` under `noImplicitAny`, while passing an incremental local typecheck whose `.tsbuildinfo` predates the new file. Caught by CI on the first push of this branch; `tsc -b --force` is the check that reproduces it locally.
- **`ChangeActionBadge` gets its regression cover retroactively.** PR #101 shipped with none available: `packages/web` had no unit-test harness on `main` at the time and the evidence was an out-of-tree axe-core run. The harness has since landed, so the assertions are backfilled here alongside the sibling fix rather than left as prose in a merged PR body.
- **This class is invisible to `eslint-plugin-jsx-a11y`.** `role-supports-aria-props` only fires once an element _has_ a role, so a role-less element passes clean — confirmed in the WIC-1185 review against the strict ruleset, all 40 rules, zero findings. The lint rule tracked by WIC-1192 would not have caught either instance; these tests are the enforcement.

### Fixed — merging an older duplicate walked a company's first-seen date forward (2026-08-26)

`mergeCompanies` reconciled `applicationCount` and `aliases` when folding duplicates together but never wrote `firstSeenAt`, so the survivor kept its own date unconditionally. Found by QA while writing the first tests for the UC-2 dedup endpoints (WIC-1360, from WIC-1354).

- **The common case is the wrong one.** Duplicates appear because a company was re-entered under a new spelling, which makes the *source* the older row — so the typical merge moved `firstSeen` forward. `firstSeen` is what the catalog reports as the start of a company relationship, so any tenure or recency reading was wrong for exactly the companies that had been deduped, i.e. dedup degraded the one field it should have improved.
- **The loss was silent and unreachable through the API.** The source is soft-deleted, `listCompanies` filters deleted rows by default, and `toCompanyDTO` surfaces `firstSeen` from the survivor alone. ### Fixed — The organic-traffic watcher's two PostHog fetches share one fault tuple, so exit `10` survives a network fault (2026-08-29)

### Fixed — The organic-traffic watcher stops reporting a measured outage as UNKNOWN, and stops letting a probe fault suppress a real first user (2026-08-27)

`organic_watch.py`'s clause-(b) health probe used a 30s timeout. Its real ceiling is the API's Postgres `connect_timeout`: `packages/api/src/db/client.ts:23` builds `postgres(DATABASE_URL, …)` and sets none, so postgres-js's default of 30s applies (`postgres@3.4.9`, `src/index.js:453`), plus TLS and edge overhead. A 30s probe timeout therefore raced the connect ceiling with no margin at all, and a lost race printed `prod DB health UNKNOWN (The read operation timed out)` for a prod that had in fact returned a clean `degraded` payload (WIC-1358).

- **UNKNOWN is not a harmless reading here.** It is indistinguishable from "never measured", and it is the one output a reader could mistake for the outage having lifted — the false-premise release that clause (b) was added to prevent, arrived at through the probe rather than the payload. The timeout is now 90s, which clears the 30s ceiling with margin. Raising it costs nothing on a healthy response, because a timeout bounds only a hang: a 4s answer still returns in 4s. Note the ceiling is an **unpinned dependency default** — `packages/api/package.json` declares `"postgres": "^3.4.4"` — so a bump that raises it silently re-opens this race.
- **This is a budget over a known ceiling, not over an observation.** Observed latency on the same exhausted prod varies widely: 25.6–27.2s on 2026-08-27 03:4xZ, ~4s at 08:2xZ. Two mechanism claims in the first draft of this entry were wrong and are corrected here (caught in review of PR #207, WIC-1636): `/health` does **not** wait on the Worker's Hyperdrive retry budget — it catches its own DB error (`app.ts:97-102`) and returns `503` itself (`app.ts:105`), so nothing propagates out of `app.fetch` for `worker.ts:13-21` to retry, prod has no Hyperdrive binding, and that budget is 150ms regardless. Nor is subrequest exhaustion the slow path: once the invocation's budget is spent the runtime refuses the connection immediately, which is the ~4s reading.
- **A health-probe fault could crash the run and suppress a real first user; it no longer can.** `http.client.HTTPException` subclasses `Exception`, not `OSError`, so it was missing from both except tuples in `prod_db_health()` and a truncated `/health` body (`IncompleteRead`, `BadStatusLine`, `LineTooLong`) escaped. Because the probe is called *before* the organic branch, the process died with exit `1` and the `CANDIDATE ORGANIC TRAFFIC` block never printed — exactly the outcome the function's docstring forbids. Measured: with one real organic event staged and the probe raising `IncompleteRead`, the run went from a traceback to a correct exit `10`. Pre-existing, not introduced by the timeout change.
- **Cloudflare edge 5xx codes are now named instead of rendered as an ambiguous fault.** A 52x never reaches the Worker, so the body is plain text and the old handler collapsed it to `HTTP 522, unparseable body`. That matters because a 52x is *not* the WIC-1386 subrequest exhaustion — exhaustion is the Worker running and answering `503` with JSON, while a 52x means it never ran at all — and conflating the two sends the next reader to the wrong card. 520–526 now render their specific cause; anything else keeps the generic wording rather than inventing one.
- **No change to the verdict or the exit code.** Health remains reporting-only, and every fault path now genuinely collapses to `unknown`. `--selftest` previously covered only the pure renderers (`classify_health`, `describe_edge_failure`); it now also stubs `urlopen` and asserts the collapse in `prod_db_health`'s except tuples, which is where that property actually lives and where it had no coverage. Both defects above survive the old suite and are killed by the new one.

### Docs — Changelog entries have an insertion convention, because the union driver never reached GitHub (2026-08-26)

### Security — App-host transport hardening (2026-08-19)

QA's WIC-1003 prod regression pass found `app.careerpin.app` — the authenticated surface, carrying Supabase session tokens, resume uploads and PII — serving the app shell over plaintext HTTP with a `200` and sending **no** security headers at all, while the marketing apex and `www` both `301` to HTTPS. Root cause: the app host is a Workers custom domain, so the zone-level HTTPS redirect that covers apex/www does not reach it, and neither the Worker nor the static-asset router was emitting hardening headers (WIC-1011).

- **Cleartext requests are redirected** — `httpsRedirect()` (`packages/api/src/middleware/security.ts`) turns away any request that arrived over HTTP before a handler runs: `301` for `GET`/`HEAD`, `308` for methods with a body so the retry keeps its method and payload. The client scheme is read from Cloudflare's `cf-visitor` — the only authoritative source at the edge — then the request URL. `x-forwarded-proto` is client-settable unless a trusted proxy rewrites it, so it is honoured only when `TRUST_PROXY_PROTO` is set; otherwise a spoofed `x-forwarded-proto: https` on a cleartext request still gets redirected. Private hosts are exempt — loopback, RFC1918/link-local literals, `*.local`/`*.internal`-style suffixes and dotless container names — so `npm run dev:api` / `wrangler dev` / Vitest, LAN and mobile testing, and container-network access by service name all stay on plain HTTP rather than being upgraded to a `:443` nothing listens on.
- **Security headers on every response** — `securityHeaders()` attaches `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` and `Content-Security-Policy: frame-ancestors 'none'`, without clobbering a value a handler already set. Responses that came out of `fetch()` — notably the `ASSETS` binding serving the SPA shell — have immutable headers, so the middleware rebuilds them rather than dropping the hardening. HSTS `preload` is deliberately withheld until the cleartext `301` is confirmed live, since preloading is not reversible on a useful timescale. A full CSP beyond `frame-ancestors` awaits an audit of the Supabase/PostHog/R2 origins the SPA talks to.
- **Static assets carry the same headers** — the asset router answers `/`, `/assets/*` and `/favicon.svg` _before_ the Worker runs, so those responses can only be hardened at the edge. `packages/web/public/_headers` (copied verbatim into `packages/web/dist/`, the `assets.directory`) declares the same five headers.
- **Fingerprinted assets are now immutable** — Vite content-hashes everything under `/assets/`, but the Cloudflare default `public, max-age=0, must-revalidate` cost a revalidation round-trip per asset per page load. Those are now `public, max-age=31536000, immutable`; `index.html` is explicitly held at `must-revalidate` so clients cannot pin to a stale build and request asset hashes that no longer exist.
- **The first-contact gap was closed at the zone, not in code** — the Worker-side redirect only covers paths the Worker actually sees (`/api/*`, `/health`, SPA deep links); `/` and `/assets/*` are answered by the static-asset router before the Worker runs, so no code change could reach them. HSTS does not paper over this: per RFC 6797 §8.1 a browser **must ignore** an HSTS header received over plain HTTP, so the `_headers` HSTS on a cleartext `/` pins nothing — the pin only lands once a client completes an HTTPS response. The actual fix was the zone-level `Always Use HTTPS` setting on the `careerpin.app` zone, enabled 2026-08-19 under WIC-1014 and verified live: `curl -sI http://app.careerpin.app/` → `301` → `https://app.careerpin.app/`, with apex and `www` unchanged. HSTS `preload` remains deliberately withheld: it is now eligible (the `301` is confirmed), but submitting the domain is a separate, hard-to-reverse decision tracked apart from this change.
- **HSTS and `nosniff` also ship from the zone, ahead of this deploy** — for the same reason the redirect had to: the asset router answers `/` before the Worker runs, and `_headers` only takes effect on a deploy. The `careerpin.app` zone `security_header` setting was enabled 2026-08-19 (WIC-1011) with `max-age=31536000`, `includeSubDomains`, `nosniff`, and `preload` **off** — byte-identical to the values in `SECURITY_HEADERS` and `_headers`, so nothing drifts when this branch lands, and `securityHeaders()` only sets a header it does not already see. Verified live on all three hosts: `strict-transport-security: max-age=31536000; includeSubDomains` and `x-content-type-options: nosniff` on `app`, apex and `www`. `includeSubDomains` is safe here because every record in the zone is Cloudflare-proxied (including a proxied `*.careerpin.app` wildcard) with `Always Use HTTPS` on, so there is no plaintext-only host to strand. The remaining three headers (`X-Frame-Options`, `Referrer-Policy`, `Content-Security-Policy`) and the immutable `/assets/*` `Cache-Control` are **not** reachable from the zone — the production API token is authorised for zone settings but not for the response-header transform ruleset (`request is not authorized`) — so those still ship only with this deploy.

### Documentation — The four remaining UC-5 report endpoints are now specified (2026-08-25)

`API_CONTRACTS.md` had no `Reports (UC-5)` section until the entry below added one, and that entry deliberately specified only `GET /api/reports/by-fit-tier` — the one endpoint with a cross-use-case contract to state. The other four shipped with UC-5 in April 2026 and had never been specified anywhere: `GET /api/reports/pipeline`, `/needs-action`, `/stale` and `/closed-loop` are now documented from the Zod query schemas in `routes/reports.ts` and the response interfaces in `types/index.ts` (WIC-1307). No behaviour changed — this records what the endpoints already do.

Three properties were undocumented and are not guessable from the response shape:

- **Summaries on the paginated reports describe the page, not the result set.** `needs-action`, `stale` and `closed-loop` compute every `summary` field — `total` included — from the current page, after `limit` is applied. `summary.total` is the length of `applications`, never a grand total, and the averages and breakdowns are page-local. A client reading `summary.total` as a result-set count under-reports by a factor of however many pages there are.
- **`GET /api/reports/stale` defaults to `applied,phone_screen`, not to all statuses.** Those are the two states where the ball is in the employer's court. Callers expecting every active application to be eligible for staleness must pass `status` explicitly.
- **`closed-loop`'s `rejectionsByStage` need not account for every rejection.** It buckets by `previousStatus`, so rejections whose history is too short to have one count toward `summary.rejections` while appearing in no bucket, and `percentage` is a share of `rejections` rather than of `total`. The percentages sum to 100 only when every rejection has a known previous stage.

Also recorded: `pipeline` and `by-fit-tier` are unpaginated and accept neither `limit` nor `cursor`; `limit` above 100 is a `400` rather than a clamp; `pipeline`'s application objects carry no `status` field because the group supplies it; and `closed-loop`'s `period` filters on `updatedAt` rather than the computed `closedAt`, so editing a closed application keeps it inside a narrow window.

The shared section also now carries the **malformed-cursor `400`** that WIC-1308 shipped (see the entry above): a `cursor` the server did not issue is a `VALIDATION_ERROR` on `needs-action`, `stale` and `closed-loop`, with **no `details`** — the second `VALIDATION_ERROR` shape on these endpoints, and the Zod block is cross-referenced so a reader does not assume every report `400` carries `details`. That block claimed the route schemas were "the authority on accepted values", which `cursor` is the one exception to — it is declared as a plain optional string and judged only when it is decoded in `reports.service.ts` — so the claim now carves it out rather than being contradicted three lines later (WIC-1316). An absent or empty `cursor` is still the first page. Two encoding leaks were closed on `main` by `172802b` (#120), not here (WIC-1311): the pagination table and the catalog-diffs table had both published the cursor as a "base64url-encoded offset" while the prose two lines below called the encoding an implementation detail — publishing the recipe is an invitation to hand-craft exactly the cursor now being rejected. This branch's `109b18c` made the same edit independently about twenty minutes later, so merging `main` in absorbed the duplicate and this change's net diff carries none of it. Both rows now say what the cursor _is_ (opaque, server-issued) rather than how it is built.

### Fixed — Every paginated endpoint now rejects a malformed cursor, from one shared decoder (2026-08-25)

WIC-1308 fixed the unguarded base64url cursor decode in `reports.service.ts`. The identical decode was inlined, unguarded, at **nine more call sites across four services** — `catalog` (six), `application`, `cover-letter`, `resume-variant` — none of which had even the unreachable `try`/`catch` the reports version started with. Both failure modes carried over verbatim (WIC-1312).

- **Encoder and decoder now live together**, in `packages/api/src/lib/pagination.ts`. `encodeCursor` was copy-pasted at all twelve sites too; that every site could _mint_ a cursor while only the reports trio could _reject_ one is precisely how the guard came to be missing in nine places. The reports service now imports both rather than owning them.
- **Reject, not fall back — at all twelve sites, including the catalog ones.** `API_CONTRACTS.md:713` publishes the catalog cursor's encoding ("base64url-encoded offset") rather than calling it opaque, which raised the question of whether a hand-crafted catalog cursor is supported. It does not change the answer: a hand-crafted cursor that genuinely _is_ a base64url non-negative offset still works, so the only requests this turns into a `400` are ones no correct client can send.
- **`GET /api/applications` is the odd one out and was checked separately**, per the ticket. Its parameter is `page`, not `cursor` — but `nextPage` is minted the same way (`Buffer.from(String(offset + limit))`), it is documented as coming "from a previous response", and no client constructs one, so the same `400` applies. Its `catch` was doubly dead: unreachable _and_ the comment above it ("start from beginning") described a fallback that would not have happened anyway. The error message names `page`/`nextPage` rather than `cursor`/`nextCursor`, so it points at something the caller can find in their own request.
- **The guard is verified to be wired in at each site, not merely to exist.** `packages/api/test/pagination.test.ts` drives all twelve real service functions with a malformed cursor and a negative one against a database handle that throws on any access — so a site that skips the guard is caught by reaching the query builder, which is the actual defect. Confirmed by mutation: restoring the inline decode at `catalog.listCompanies` and `application.listApplications` fails exactly their four cases, each reporting `db.select was reached with a malformed cursor`. The `parseCursor` unit cases move here from `reports.service.test.ts` alongside them. API suite: 411 passing.
- **The coverage table is now counted rather than trusted (WIC-1335).** Its first draft listed only the nine sites this change converted and omitted the three in `reports.service.ts` — the ones WIC-1308 was about — so its own claim that "reverting any single site fails its case here" was false for a quarter of the codebase. Measured on review: reinstating the exact pre-WIC-1308 decode in `getNeedsActionReport` left the whole suite green. The three rows are added, and a companion case now compares `parseCursor` call sites found in `src/services/*.ts` against the table **per service**, so neither a new paginated endpoint nor a swapped row can shrink the claim silently. Confirmed by mutation in both directions: each reports site now fails its own two cases, and dropping a row — or trading one service's row for another's, leaving the total unchanged — fails the counter.
- **The error message no longer infers the response field from the request parameter.** It built the field name as `next${param === 'page' ? 'Page' : 'Cursor'}`, so a future endpoint spelling its parameter anything else would have been told to pass back a `nextCursor` its response does not contain. `parseCursor` now takes both names as one `{ param, responseField }` value (`CURSOR_NAMES`, `PAGE_NAMES`). The two messages that exist today are byte-identical to before — this closes a latent trap, it does not change the contract.
- **Documentation divergence found, not fixed here** — `API_CONTRACTS.md` documents the applications list parameter as `cursor` returning `nextCursor`; the implementation has always used `page`/`nextPage`. A client following the document sends `cursor=…`, which the Zod schema drops silently, so it receives page one forever with no error. Pre-existing and independent of this change; handed to the Technical Writer with the cursor-contract update.

### Fixed — By-fit-tier tile blurbs no longer contradict the tier they label (2026-08-25)

Each tile on `GET /api/reports/by-fit-tier`'s page carried a one-line blurb describing its tier, and every blurb restated only the **match-percentage** arm of `computeRecommendation`. That function is an ordered four-way cascade over _three_ variables — match percentage, critical-gap count, and the seniority flag — so a tier fires far outside the percentage band its blurb claimed. Found reviewing PR #111 (WIC-1309); the tiles are `opacity-50` placeholders rendering `—` today because UC-3 analyses are not persisted, so nothing user-visible has shipped wrong yet.

- **Measured, not argued.** Exercising the real `computeRecommendation` over every reachable `(match %, critical gaps, seniority)` triple at `totalRequired = 20` — 574 cases, match percentage in half-steps because partial matches weigh 0.5 — the shipped blurbs were false for **81 of them (14.1%)**. The worst case: a 100% skill match with 3 critical gaps returns `moderate_fit`, so the tier would have been captioned **"50–79% of required skills"** — contradicting its own definition, and contradicting the **"You match 20 of 20 required skills"** the same user reads when they drill into the application. (The number on the tile itself is the count of applications in that tier, not a skill-match count; no skill-match count is rendered on the report page.) The independently-reported figure on a coarser 252-case grid was 32 (12.7%).
- **Blurbs are now necessary conditions of their tier, never sufficient ones.** A tile has no room to restate a cascade and does not need to; what it must never do is make a claim its own tier can violate. Each of the four now carries the gap and seniority conditions that can pull a tier down. Re-measured over the same grid: **0 violations.**
- **The invariant is enforced, not just fixed.** `packages/api/test/fit-tier-blurbs.test.ts` pairs each shipped string with a machine-readable predicate, checks it against the real scorer over the whole grid, and re-reads the strings **out of `ReportsByFitTier.tsx`** — cross-package on purpose, because the copy lives in `web`, the rule lives in `api`, and nothing else connected the two. Reword a blurb without revisiting its predicate and the API suite fails. A companion assertion pins that all four tiers are actually reached, so the check cannot pass vacuously. Confirmed by reversal: restoring the original blurbs fails it with 81 named counterexamples.
- **The source doc had the same defect and is corrected in the same change.** `docs/architecture/API_CONTRACTS.md`'s scoring bullets (pre-existing, and almost certainly where the blurbs were copied from) read as four exclusive percentage bands. They are an **ordered cascade**: the first rule that matches wins, so a tier's range is not bounded above by the tier before it. `strong_fit`'s ≤1-critical-gap condition was unstated, `moderate_fit` was documented as 50–79% when it fires up to 100%, `stretch` did not mention the >3-critical-gap route into it, and `low_fit` omitted that it also requires no seniority mismatch.
- **Wording is provisional.** The strings are the Copywriter/Editor's to rule on (WIC-1318); the constraint this change locks down is truth, not phrasing.

### Fixed — A malformed report cursor is now a `400`, not a silently wrong page (2026-08-25)

`decodeCursor` in `reports.service.ts` wrapped its body in a `try`/`catch` that **could not fire**. `Buffer.from(s, 'base64url')` does not throw on invalid input — it discards characters outside the alphabet and decodes whatever is left, down to an empty buffer — so the intended "fall back to the first page" never happened. `parseInt('', 10)` returned `NaN`, and `NaN` is a value, not an exception: it flowed straight through to `.offset()` in all three paginated reports (`needs-action`, `stale`, `closed-loop`). Found while specifying those endpoints for WIC-1307 (WIC-1308).

- **The observed symptom was a silently wrong page, not the expected `500`** — the ticket predicted a Postgres syntax error. Drizzle in fact **omits the `OFFSET` clause entirely** when the value is falsy, and `NaN` is falsy, so `?cursor=not-base64!!` quietly returned page one. That is the behaviour the dead `catch` intended, arrived at by accident: a Drizzle internal, not a contract, and one that would change under it without warning. Verified against `drizzle-orm` + `postgres-js` by inspecting the generated SQL for `offset(NaN | 0 | 50 | -5 | 1.5 | Infinity)`.
- **A hand-crafted negative cursor was a genuine `500`** — this was not in the report. `LTU` (base64url of `-5`) decodes to `-5`, which is _not_ falsy, so it survives as `OFFSET $2` with a parameter of `-5` and Postgres rejects it (`OFFSET must not be negative`). The caller could not have diagnosed that from an `INTERNAL_ERROR` response.
- **Rejecting beats falling back.** `decodeCursor` is replaced by `parseCursor`, which returns `400 VALIDATION_ERROR` for any cursor this module did not issue. The cursor is opaque and server-issued, so a client that echoes `nextCursor` back verbatim can never reach that branch; one that does has a bug, and serving page one both hides it and invites an endless pagination loop. An absent or empty `cursor` is still the first page — those are indistinguishable at the query-param layer.
- **The digit check is load-bearing, and `Number.isSafeInteger` alone is not enough** — `Number('')` is `0`, so a cursor decoding to nothing (`'!!!!'`) would still have silently meant page one; a negative offset _is_ a safe integer; and `parseInt` would have accepted `'50junk'` as `50`. `isSafeInteger` still catches the remaining case, a digit string too large to survive `Number` intact. Confirmed by mutation: restoring the original body fails 8 of the new tests, and keeping `isSafeInteger` while dropping the regex still fails 3 (empty decode, negative, surrounding whitespace).
- **Validated in the service, not the route schema** — the encoding a cursor must match lives with `encodeCursor`, so duplicating a decoder in a Zod `refine` would put the two out of reach of each other. The thrown `AppError` reaches the client through `app.onError` in the same `{ error: { code, message } }` envelope the route's own schema rejections use; a route test pins that path.
- **The same pattern is unfixed in five other services** — `application`, `catalog` (six call sites), `cover-letter` and `resume-variant` all inline the identical `parseInt(Buffer.from(cursor, 'base64url')…)` with no guard. Filed separately rather than folded in here, since each endpoint's fallback-vs-reject choice is its own contract decision.

### Changed — One judgement, one enum: `FitTier` is now `recommendation` plus its two no-verdict states (2026-08-25)

Two types described the same judgement at different granularity, and the relationship between them was written down nowhere. `FitRecommendation` (UC-3, `POST /api/catalog/job-fit/analyze`) was `strong_fit | moderate_fit | stretch | low_fit | null`; `FitTier` (UC-5, `GET /api/reports/by-fit-tier`) was `strong_fit | moderate_fit | weak_fit | not_analyzed`. They agreed at the top and split at the bottom. `FitTier` is now **defined as** `FitRecommendation | 'unscored' | 'not_analyzed'`, so a report groups applications by the verdict the analysis actually reached, at the granularity it reached it (WIC-1298, spun out of WIC-1288).

- **`weak_fit` is gone; `stretch` and `low_fit` are distinct tiers (wire change)** — `stretch` is not a magnitude. `computeRecommendation` returns it on a _seniority_ mismatch even at a good skill match, so folding it into a bucket named "weak" told the user their skills were short when the finding was that the level was wrong — the opposite action. Reporting a coarser judgement than the one that was made loses the reason, not just the precision.
- **`unscored` splits "ran and could not score" out of `not_analyzed` (wire change)** — `recommendation: null` is a _result_: an empty catalog, or a job description in which no required skills were found (`totalRequired === 0`). `not_analyzed` means no analysis exists. One is fixed by fixing the catalog or the JD, the other by running the analysis; `not_analyzed` had been standing in for both. `summary.analyzed` counts `unscored` as analysed, and both counters are now derived from the groups rather than hardcoded.
- **Breaking in principle, inert in practice — and only at this exact moment.** Removing `weak_fit` and re-tiering `not_analyzed` versions the endpoint. But UC-3 analyses are not persisted (there is no `job_fit_analyses` table and `applications` carries no analysis reference), so `getByFitTierReport` hardcoded `not_analyzed` for every row and this endpoint has **never emitted a non-zero `weak_fit` count**. No client can depend on a value the server has never produced. The same change made after UC-3 persistence lands would be a real migration; the cost was at its minimum now and rising.
- **The mapping is a function, and it is specified** — `recommendationToFitTier()` in `reports.service.ts` is the single place the two vocabularies meet, and it takes the _analysis_ (or `null` for "none exists") rather than a bare recommendation, so the absent-vs-null distinction cannot be lost at a call site. `API_CONTRACTS.md` gains a `Reports (UC-5)` section documenting the endpoint and the mapping table. Six unit tests pin every arm, including the two "these must not be equal" cases — the mapping is otherwise unreachable from the API until persistence lands, so all but one arm would have shipped untested.
- **The two can no longer drift apart** — because `FitTier` is a union _of_ `FitRecommendation`, adding a recommendation member propagates by construction and fails `npm run typecheck` at `FIT_TIER_ORDER` until the new tier is ranked. An unranked tier would otherwise vanish from `groups` and `byTier`, silently dropping applications from a report that claims to cover the pipeline. Verified with three negative controls: adding a `FitRecommendation` member fails naming `"wildcard"`; dropping `stretch` from `FIT_TIER_ORDER` fails naming `"stretch"`; dropping `unscored` from `FIT_TIER_LABELS` fails naming the missing property.
- **The display-side workaround dissolves** — `FIT_TIER_LABELS` (added the same day by WIC-1288) had a hand-written `weak_fit: 'Weak fit'` entry precisely because that member had no `Recommendation` counterpart to borrow a label from, and the code comment said so. It is now `{ ...FIT_LEVEL_LABELS, unscored, not_analyzed }` — every fit level is spelled once. `unscored` reuses `NO_FIT_LEVEL_LABEL`, since it names the same condition the analysis screen already labels.
- **The by-fit-tier page renders the tiers it actually has** — its three hard-coded placeholder tiles (`strong_fit` / `moderate_fit` / `weak_fit`) became a four-tile grid over the verdict tiers, with `unscored` and `not_analyzed` given their own row apart from them: those are states of the analysis, not judgements about the job, and a tile invites comparison against a real fit level. Tile blurbs now restate the actual scoring thresholds instead of "High/Medium/Low match score", which was wrong for `stretch`.
- **Also corrected: the documented condition for `recommendation: null`.** `API_CONTRACTS.md` said "Catalog is empty (see `catalogEmpty: true`)". `computeRecommendation` also returns `null` whenever `parsedJd.requiredStack` is empty, with `catalogEmpty: false` — a second, unmentioned cause that a client checking `catalogEmpty` would mis-handle.

`JobFitAnalysis` spent the word **`moderate` on two unrelated scales at once**: `recommendation: 'moderate_fit'` rendered "moderate fit" near the top as a verdict about the whole application, while `GapSeverity: 'moderate'` rendered "moderate" on each gap card below as one shortfall's severity. The ladder reads yes / maybe / reaching / no. ### Accessibility — ALL-CAPS strings moved out of the DOM into the Overline token (2026-08-19)

Six render sites spelled all-caps labels directly into the DOM. Caps baked into markup are what the accessibility tree receives, and some screen readers — VoiceOver notably — spell short all-caps strings out letter by letter; `text-transform: uppercase` renders caps visually while leaving the accessible name normal-cased. This is **known-good practice, not a WCAG conformance fix** — no success criterion was failing. Copy + `className` only, no logic changes (WIC-1069, implementing the corrections in WIC-1086).

- **Headings de-shouted (visible change)** — `QuickReferenceExport`'s `<h1>` is now "Interview quick reference" and `GapMitigationPanel`'s `<h4>` is "Key strengths to highlight". These are headings that happened to be shouted, not overlines, so the caps are dropped rather than re-applied in CSS. `AmbiguityResolver`'s three card titles ("Ambiguous tag", "Unresolved wikilink", "Fuzzy match") are `<h3>` titles by the same rule; dropping the caps there also avoids uppercasing the adjacent user-authored `item.value` that shares the element.
- **Badges keep their caps (no visible change)** — `GapMitigationPanel`'s severity badge is a genuine Overline-token badge, so the source string is normal-cased and `uppercase` is applied via `className`, matching the existing `MobileNavigation` / `CatalogBrowseTable` precedent. The two `.toUpperCase()` call sites in `JobFitAnalysis` retain their existing caps treatment by the same mechanism, but they are not badges — they are 20px and 14px inline sentence fragments, not the 10px/600 Overline token — so re-applying `uppercase` there preserves the current visual without claiming the token. Whether to keep that visual at all was deferred to WIC-1122. Each `JobFitAnalysis` site gets its own wrapping `<span>` because both sit inline beside sibling prose that must not be shouted.
- **`.replace('_', ' ')` retained deliberately** — `JobFitAnalysis` renders the API's underscored `FitRecommendation` enum (`moderate_fit`), so only `.toUpperCase()` was removed. Dropping the whole chain would render `moderate_fit` and break `job-fit-analysis.spec.ts:342`, `:421`, and `:574`, which match case-insensitively but not across an underscore. Confirmed by running the spec with the `.replace()` removed as a negative control (3 failures), then restored (18 passed, 2 pre-existing skips).

### Accessibility — `EmptyState` no longer leaks its action button out from behind an open modal (2026-08-19)

`EmptyState` carried `aria-live="polite"` on the container that wraps its action button. The `aria-hidden` package Radix Dialog uses to hide the background behind a modal **deliberately exempts `[aria-live]` elements** (`aria-hidden@1.2.6`, `dist/es2015/index.js` L131-133), and exempting a node keeps that node, all of its descendants, and its entire ancestor chain reachable to the screen-reader virtual cursor. On any page rendering `EmptyState`, opening a dialog therefore left `#root`, `<main>` and the empty state's **"Create Your First Project"-style action button** live and reachable behind the modal.

- **Fix** — dropped `aria-live="polite"` from `EmptyState`. The content is static per `variant` and never updates in place, so the live region announced nothing that ordinary content traversal would not; it only bought the modal-hiding exemption. It did not even do its stated job: the component is _inserted_ by a load-state branch, and a live region that arrives already populated is not reliably announced.
- **Design verdict** — `role="region"` and `aria-label="Empty state"` were dropped in the same change, which is the call WIC-1155 routed to UI/UX rather than fixing inline. A `region` is a navigable landmark reserved for major structural areas; an icon, a heading, one sentence and at most one button is not one, and this block is the only content inside `<main>` when it renders, so the landmark wrapped the sole contents of another landmark. The heading is the entry point users navigate by, and "No documents found" describes the content better than the component's own name. The two could not be split: `aria-label` on a role-less `<div>` maps to `generic`, which supports no accessible name, so keeping it would have left a dead attribute that axe flags as `aria-prohibited-attr`. The wrapper is now a plain `<div>`.
- **Root cause closed** — `docs/design/COMPONENT_SPECS.md` §10 is where this came from: its Accessibility block instructed implementers to "**ARIA Live:** Announce when empty state appears", and the component followed the spec faithfully. That block now specifies no-ARIA and records why, so the defect is not re-derived. The same block's "**Focus:** Action button receives focus" directive was corrected at the same time — it was never implemented, but an empty state renders _as the result of_ a user action, so focusing its button would yank focus out of the filter input the user is still typing into.
- **Audit** — the three other `aria-live` sites (`KanbanBoard` drag announcer, `OnboardingProgressIndicator`, wizard `ProgressIndicator`) are genuine live regions that each sit on a dedicated `sr-only`/text-only node. They take the same exemption, but because they wrap no actionable content and their siblings are still hidden, nothing reachable leaks. They are deliberately left as-is.
- **Verified** — a negative control run against the real `aria-hidden` package reproduces the bug on the pre-fix DOM (`#root` unhidden, action button reachable, header/tab bar correctly hidden — matching the behaviour measured on `/projects`) and confirms the fix (`#root[aria-hidden="true"]`, action button unreachable, dialog itself still reachable).
- **The general rule is now written down, and it is about mount point rather than about `EmptyState`** — `docs/design/ACCESSIBILITY.md` had no guidance on where a live region may be mounted, and its own toast-container example was exactly the failing shape. Its Live Regions section now states that an **app-level** announcer must be `createPortal`-ed outside `#root`, with the do/don't pair, because `aria-hidden@1.2.6` keeps not just the `[aria-live]` node but its **entire ancestor chain** (`dist/es2015/index.js` :133 collects the targets, :48-52 walks each one up its `parentNode` chain into `elementsToKeep`) — so one in-page announcer anywhere under `#root` leaves `#root` itself unhidden behind every dialog. Component-local announcers (a progress indicator, the board's drag announcer) may stay in place, which is why the WIC-1155 audit above correctly left three of them alone. The failure is silent — the dialog opens, focus still traps, sibling subtrees are still hidden — so only an explicit `#root[aria-hidden]` assertion catches it, and it has already cost a test run: PR #115's in-place `ResumeManager` announcer broke PR #95's existing assertion and was fixed by portalling to `<body>`. The keyboard-testing checklist now asks for that assertion against an **empty-list** state, since a populated fixture is how the invariant hid here in the first place (WIC-1467, PR #157, `3f785e3`).

Found during WIC-1141 (PR #97) and split out so an app-wide presentational change would not ride along with that modal migration. (WIC-1155)

### Fixed — Unmatched in-app URLs now show a 404 page instead of blank app chrome (2026-08-19)

The client router had no catch-all. React Router renders `null` for an unmatched path, so a typo'd or stale in-app URL produced the navigation chrome wrapped around an **empty `<main>`** — no error, no message, and no way for a user to tell a broken link from a page that was still loading. WIC-1004's SPA fallback made this quieter rather than louder: the Worker now correctly returns `200` + shell for any unmatched non-API path, so what used to be a plaintext `404` became a silent blank page. This is the client-side half (WIC-1036).

- **`NotFound` page** (`packages/web/src/pages/NotFound.tsx`) — states that the page was not found, echoes the requested path so a typo is distinguishable from a broken link, and offers "Back to dashboard" plus a "Go back" affordance (rendered only when there is history to go back to). Focus moves to the heading on mount so screen-reader and keyboard users are told the navigation landed somewhere unexpected.
- **Catch-all route** — `<Route path="*" element={<NotFound />} />` is now the last entry of the inner `<Routes>` in `packages/web/src/App.tsx`. It sits inside the app shell, so navigation stays available from the 404.
- **`/dashboard` now redirects rather than 404ing (WIC-1054).** `/dashboard` is not a route — the Dashboard is `/` — but it shipped in four call sites (the final onboarding CTA and three breadcrumbs) and is therefore in real bookmarks and browser histories today. Before the catch-all those URLs rendered blank chrome; after it they would have rendered a 404, which is a clearer wrong answer but still the wrong screen, and worst at the moment a brand-new user finishes onboarding and clicks "Go to Dashboard". `<Route path="/dashboard" element={<Navigate to="/" replace />} />` now sits with the other routes, above the catch-all. `replace` keeps the dead URL out of history, so the back button cannot lead into the page the user just escaped. Correcting the call sites (WIC-1032, WIC-1041) is still required and still tracked separately — this redirect catches links already in the wild, it does not license new ones.
- **Outer `<Routes>` needs no change — confirmed, not assumed.** `/*` already funnels every non-`/login` path through `ProtectedRoute`, so an _unauthenticated_ unmatched path still redirects to `/login` rather than reaching the 404. Covered by a regression test.
- **Coverage** — `packages/web/e2e/not-found.spec.ts` (7 Playwright specs, mock auth, no backend required): the 404 renders on an unmatched path, names that path, keeps app chrome and returns to the dashboard, does not swallow a real route, `/dashboard` reaches the Dashboard rather than the 404, that redirect replaces history instead of stacking onto it, and the unauthenticated case still redirects to `/login`. The two redirect specs were confirmed to fail with the route removed, so they discriminate rather than merely pass.
- **Design pass applied (WIC-1051).** The 🧭 emoji illustration is replaced by an inline outline SVG matching `TopNavigation`'s icon style — emoji are host-OS rendered, so they vary by platform and are absent on some, a poor trade on the one screen a user reaches when something has already gone wrong. The content block is now vertically centred within `min-h-[60vh]` instead of sitting against the top of a tall empty column. The requested-path readout is **kept but demoted** below the actions: it is the one element that distinguishes "I typed this wrong" from "this app is broken", but it is diagnostic rather than directive and should not sit in the path to the buttons. It is now borderless `text-caption`, with the path elided at 120 characters (full value in `title`) so a hostile or absurd URL cannot blow out the layout.
- **Accessibility fixes in the same pass.** The path-readout label was `neutral-500` on a `neutral-100` panel, which measures **4.39:1 — a WCAG AA failure** for normal text; dropping the panel and moving the label to `neutral-600` on `neutral-50` takes it to 7.2:1. The eyebrow and keyboard hint moved `neutral-500` → `neutral-600` for the same reason (4.63:1 → 7.2:1, i.e. off the AA borderline).
- **"Go back" gating corrected.** It was keyed on `window.history.length > 1`, which counts the whole tab session — a cold deep-link from an external site (email, Slack) reports length 2, so the button rendered and `navigate(-1)` would have ejected the user out of the app entirely. Now keyed on React Router's `location.key !== 'default'`, which is true only after an in-app navigation.
- **Copy pass applied (WIC-1052).** Strings are isolated in a single `COPY` block at the top of `NotFound.tsx`, so the wording revision was a one-hunk diff that could not disturb layout. The heading is now "That page couldn't be found" — focus moves to the `<h1>` on mount, so it is the first thing a screen-reader user hears and has to stand alone; the actorless passive avoids a first-person-plural "we" that no other screen in the app uses, and "couldn't be found" claims less than "doesn't exist" (the app cannot know whether the page never existed or was deleted). The body drops from 128 to 92 characters and reassures in the positive — "Everything you've saved is safe" rather than "Nothing you tracked has been lost", which named the loss it was denying. The eyebrow is "404" rather than "Error 404": the digits are the searchable, quotable part, and "Error" was the harshest word on an otherwise gentle page. "Requested path:" becomes "Address you tried:" — plain English for a footnote whose job is to let a user spot their own typo. The primary action is **"Back to dashboard"** (WIC-1054). The copy pass had kept "Go to dashboard" to agree with the top nav's "Dashboard" label, but that was settled before the collision was raised: the final onboarding CTA reads "Go to Dashboard", so the two buttons had the same accessible name modulo case. A 404-recovery click and a completed-onboarding click are opposite signals, and anything keyed on the label — analytics, and `getByRole('link', { name: … })` selectors — could not tell them apart. This narrows that collision rather than closing it: `ApplicationDetail.tsx` renders a link to `/` named `← Back to Dashboard`, which a case-insensitive name selector still matches. Test selectors are safe because the two never co-render, but label-keyed analytics remains ambiguous; the durable fix is an explicit event property, not a string. ### Infrastructure — Deploy-pipeline gates: unbuilt PRs, an advisory preflight, and Access-gated previews (2026-08-19 → 2026-08-26)

Four independent holes in `.github/workflows/deploy.yml`. Three of them made a PR _look_ safer than it was.

- **A stacked PR ran no checks at all — and therefore read as more mergeable than a tested one.** The workflow triggered on `pull_request: branches: [main]`, which filters on the **base** branch, so any PR stacked on another PR built nothing. Measured across the 15 open PRs at the time: 13 main-based PRs green, #92 and #93 with **zero** check runs. With no required check to report, those two rendered `MERGEABLE / CLEAN` while the 13 genuinely-green ones showed `BLOCKED` on `REVIEW_REQUIRED` — the untested PRs looked the most merge-ready in the repo. The base filter is now `'**'`. Production cannot be reached this way: `deploy-production` is gated on `if: github.event_name == 'push'` and `on.push.branches` stays `[main]`, so no `pull_request` event can satisfy it whatever base it targets (WIC-1138, PR #94, `9640312`).
- **A CI skip marker reproduced the identical hazard, and was not fixable from inside `deploy.yml`.** A skip directive suppresses both the `push` and the `pull_request` event, so a PR carrying one also reports zero check runs — and a guard living in `deploy.yml` would be suppressed by the very commits it exists to catch. `.github/workflows/skip-ci-guard.yml` therefore runs on `pull_request_target`, which is not skippable, and fails a PR **only** when a skip marker is paired with a change outside `docs/**`, `*.md` and `.github/workflows/**`; docs-only and workflow-only skips remain a deliberate, untaxed route. It never checks out or executes head code — no `actions/checkout`, no `run:` step — and downgrades its own token to `contents: read` + `pull-requests: read`. One measured finding changed the design: the marker does not have to sit in the subject line. PR #100's head was rebased specifically to drop `[skip ci]` from its subject and **still** had zero check suites, because the commit body _explained_ the marker in prose, inside backticks, 26 lines down. Writing _about_ `[skip ci]` skips CI, so the guard matches the whole message and its failure text says so (WIC-1212, PR #104, `38f2b98`).
- **The production credential preflight is now a hard gate, ahead of the migration step.** It ran with `continue-on-error: true` _before_ `Run database migrations`, so a present-but-invalid `CLOUDFLARE_API_TOKEN` would migrate the production database and only then fail at the R2 and `wrangler deploy` steps — production schema advanced, the Worker code that depends on it never deployed. That is strictly worse than a clean early abort; it needs a manual rollback or a forward-fix under time pressure. The flag is dropped, which is sufficient because `packages/api/src/preflight.ts` already `process.exit(1)`s on a failed authenticated ping. The in-file precondition — _"flip to a hard gate once green in live runs"_ — was met by production deploy run `32191251045` on 2026-08-18, where the preflight step concluded `success` against the live prod token. **Production job only:** the `deploy-preview` copy stays advisory and now records why, since the dev `CLOUDFLARE_API_TOKEN` is independently dead under WIC-760 and hard-gating preview would only move an already-failing deploy's failure earlier while masking unrelated PR feedback (WIC-1009, PR #78, `0bdd2ea`).
- **QA could not verify any PR before it reached production.** The preview Worker's shared hostname sits behind Cloudflare Access — `GET /dashboard` `302`s to `cloudflareaccess.com` — and every open PR deploys to that same `jobtrail-preview` Worker, so even with a credential the build being served is whichever PR deployed most recently, not the one under review. Cloudflare also exposes each uploaded version at `https://<first-8-of-version-id>-<worker>.<subdomain>.workers.dev`, which is **not** Access-gated and is pinned to a single build, so both problems close without touching an Access policy. The preview job now parses `Current Version ID` out of `wrangler-action`'s `command-output` and publishes that host in the PR comment it already posts, as **QA / no-login URL**; if the id cannot be parsed the step logs why and the comment falls back to manual instructions rather than failing the job. Verified against PR #80's recorded run (`32222392139`): `GET /` and `GET /dashboard` return `200 text/html` and `GET /api/health` returns `401 application/json` with no Access credential of any kind, against `302/302/302` for the same three probes on the shared hostname. ### Design — One tokenised gap-severity scale, replacing three disagreeing ramps (2026-08-19)

The same three `GapSeverity` values were rendered through three different colour scales, two of them on the same element: `JobFitAnalysis`'s card left border ran red-500 / orange-500 / yellow-500, its emoji on that same card ran 🔴 / 🟡 / 🟢, and `GapMitigationPanel` ran 🔴 / 🟠 / 🟡. So `minor` was **yellow by border and green by emoji on one card**, and the middle and low steps were effectively swapped between the two screens. `docs/design/DESIGN_SYSTEM.md` now defines a single `--gap-severity-*` scale in three roles, plus the `caution` (orange) semantic ramp it needed — orange previously existed only as a raw hex in `--status-phone-screen`, which now references it. Docs only; the component half is tracked separately (WIC-1146, PR #96, `9ee7b39`).

- **The green was the worst of it.** Every gap is a shortfall — a low-severity gap is still a gap, never a success — so 🟢 told the user a deficiency was an achievement. That settles which existing ramp wins: `GapMitigationPanel`'s red→orange→yellow never leaves negative valence.
- **No red→orange→yellow ramp is legible under colour-vision deficiency.** At a uniform `-700` step, `moderate` and `minor` simulate to `#7a7a00` and `#797900` under deuteranopia — **1.01:1, the same colour**. Red, orange and yellow share a confusion line, so no better choice of shade inside that range fixes it. Colour is therefore demoted to _reinforcement_ and the **text label is the normative carrier** (WCAG 1.4.1). The steps chosen — red-900 / orange-700 / **amber**-600 — recover what the hue range permits: worst case **1.41:1** across the three dichromacies, against 1.01:1 before. `minor` is amber rather than yellow for exactly that reason.
- **Two thirds of the shipped borders fail WCAG 1.4.11 today** — `border-orange-500` measures 2.80:1 and `border-yellow-500` **1.92:1** against white, both under the 3:1 non-text bar. Not previously tracked.
- **The emoji are deleted rather than recoloured.** An emoji is untokenisable (the platform font owns the hue), screen-reader-noisy (🔴 announces "red circle"), and a colour-only third signal on a card that already carries a border and a word. Nothing replaces them — a swatch would have the identical defect.

When the prod `SUPABASE_ANON_KEY` moved from an RLS-bypassing `sb_secret_` key to a browser-safe `sb_publishable_` (anon) key, any direct PostgREST call to the project had to stop leaking data — which only holds if RLS is actually enforced in prod. It was not guaranteed: the original RLS SQL (`0001`) was stale and was **never wired into the deploy pipeline** (the drizzle migrator only runs `packages/api/src/db/migrations`) (WIC-905, PR #56, merged `b463b44`).

- **Current-schema RLS migration** — `supabase/migrations/0002_rls_current_schema.sql` is idempotent and existence-guarded: `ENABLE ROW LEVEL SECURITY`, own-row policies scoped `TO authenticated` (`auth.uid() = user_id`), and `REVOKE ALL` from `anon` on every user-scoped table. `0001_rls_user_isolation.sql` is marked deprecated / do-not-apply.
- **Coverage derived from the database, not a hand list** — a code-review catch (WIC-914) found the first cut hard-coded 16 tables and omitted 5 live user-scoped ones (`projects`, `company_catalog`, `job_fit_tags`, `tech_stack_tags`, `recurring_themes`). The migration and verifier now derive the table set dynamically, at deploy time, from every `public` base table with a `user_id` column in the **deploy database** (no hand-maintained list). The current schema defines **21** such user-scoped tables (`packages/api/src/db/schema.ts`); the deploy-time verifier secures and checks those present in the database it connects to, so its count reflects live state rather than the code schema. Two user-scoped tables — `onboarding_status` and `personal_info` — were not covered by this pipeline pass and were secured directly in production under WIC-926 / WIC-927 (see the _"RLS closed on `onboarding_status` & `personal_info`"_ entry above); the underlying drizzle journal gap — which kept migrations `0012+` from running in CI — has since been reconciled in **WIC-930** (PR #67, `f635129`), so those checked-in RLS migrations now apply on a fresh CI database.
- **Fail-closed verification** — `apply-rls.mjs` / `verify-rls.mjs` (`npm run db:rls` / `db:rls:verify`) apply the policies then fail the build if any user-scoped table lacks RLS or still grants `anon` access. `deploy.yml` runs apply + verify right after `db:migrate` on both preview and production, so a redeploy self-verifies and cannot ship an unsecured DB. `supabase/verify-rls.sql` is a read-only status report for the Supabase dashboard.
- **App runtime is unaffected** — the Worker reaches Postgres as the `postgres` owner role, which bypasses RLS, and the SPA calls `/api`, never Supabase directly. Verified end-to-end against local Postgres: pre-fix `anon` reads all rows; post-fix `anon` is denied and an authenticated caller sees only its own row. _(Correction, 2026-08-29: this bullet originally attributed the connection to Hyperdrive. The `hyperdrive` binding moved to `env.preview` only in `4d379b8` (2026-05-06), months before this entry, so production was already on the `DATABASE_URL` path when it was written. The owner-role conclusion is unchanged; only the path is.)_

- **Secret scanner:** new `npm run scan:secrets` CI step fails the build when secret-shaped

### Security — Credential precedence contract & registry (ADR-0001 Pillars 2 & 4, 2026-08-08)

Two canonical, **metadata-only** docs now govern how the fleet resolves and tracks every credential — the doc half of ADR-0001. No secret values are stored; both files are committed and covered by the Pillar 3 secret-scan (WIC-880, PR #63).

- **Precedence & provenance contract (Pillar 2)** — `docs/architecture/CREDENTIAL_PRECEDENCE.md` names one **authoritative source** per credential and a defined precedence order for its derived copies. Three rules: (1) one authoritative source, all other locations are derived copies reconciled _to_ it; (2) **`unset` beats `invalid`** — an absent source falls through, but a present-but-invalid one is a hard failure, never silently overridden (the WIC-855/859 GitHub env-shadow class); (3) no secret is ever set to a placeholder value. The executable half of this contract already ships in the Pillar 1 preflight's `GITHUB_TOKEN` env-shadow check.
- **Credential registry (Pillar 4)** — `docs/architecture/CREDENTIAL_REGISTRY.md` is the canonical inventory: one row per credential with owner, least-privilege required scopes, rotation cadence, next-review/expiry date, and authoritative source. Seeded for the four ADR-named providers (GitHub, Cloudflare, Supabase, Anthropic) plus incident-history providers (Gemini, Twilio) and emerging (PostHog). The scope column is the provisioning checklist that catches the WIC-869 Cloudflare mis-scope class; every row carries a review date so stale/mispointed creds (WIC-863/868 Supabase) surface on schedule.
- Both are linked from ADR-0001 and cross-linked with `docs/architecture/CLOUD_ENV_SECRETS.md` (env-var locations per environment).

### Added — UC-2: Master Catalog Index (2026-04-24)

A normalized, queryable knowledge base of professional attributes automatically extracted from resumes and applications, with human-in-the-loop review for ambiguous or uncertain extractions.

#### Features

**Catalog API** (`/api/catalog/*`)

- `GET/POST /catalog/diffs` — list and generate extraction diffs
- `GET /catalog/diffs/:id` — retrieve full diff with changes and review items
- `POST /catalog/diffs/:id/apply` — approve all, reject all, or make partial decisions
- `POST /catalog/diffs/:id/resolve` — resolve a single change or review item
- `DELETE /catalog/diffs/:id` — discard a pending diff
- `GET /catalog/companies`, `POST /catalog/companies/merge` — browse and deduplicate company entries
- `GET /catalog/tags/:type`, `PATCH /catalog/tags/:type/:id`, `POST /catalog/tags/:type/merge` — manage job-fit and tech-stack tags
- `GET /catalog/quantified-bullets` — browse extracted metric achievements by impact category
- `GET /catalog/themes` — browse recurring career themes, with core-strength promotion at 3+ occurrences

**Extraction engine** (`extraction.service.ts`)

- Detects 60+ known technologies with aliases and legacy flags (e.g. jQuery, CoffeeScript)
- Extracts 14 job-fit signal patterns across role, industry, seniority, and work style
- Identifies 9 recurring career theme patterns
- Parses quantified bullet points with dual-metric support and approximate-value detection
- Resolves `[[wikilink]]` patterns against the `wikilink_registry` for cross-reference linking
- Flags ambiguous values (`PM`, fuzzy matches) as `ReviewItem` entries for human resolution

**Diff Review UI** (`/catalog` route)

- Tab-based Catalog browse page: Pending Diffs, Companies, Tech Stack, Job Fit, Quantified Bullets, Themes
- `DiffReviewModal` — approve all, reject all, or selectively apply individual changes
- `AmbiguityResolver` — radio-button UI for resolving ambiguous tags, fuzzy matches, and unresolved wikilinks
- `ChangeListItem` — before/after diff display with checkbox selection and action badges (CREATE / UPDATE / DELETE)
